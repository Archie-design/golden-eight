# Design

## Context

`components/CalendarGrid.tsx` 已經有「點擊展開備註面板」的成熟互動（目前用於打卡備註與請假事由，見 `leave-status-visibility` 變更），只是點擊條件目前限制在 `noteFor(day)` 回傳非空字串才可點（即有備註或請假事由的日子）。`GET /api/stats/dashboard` 的 `calendar[]` 每日物件目前只有聚合的 `score`，沒有展開的 `tasks: boolean[8]`——但這份原始資料在 API 組裝 `calendar[]` 時已經從 `monthRecs`（`checkin_records` 查詢結果）取得，只是沒有被帶入回傳物件。

見 proposal.md - Why / What Changes；規格見 `specs/dashboard-stats/spec.md`。

## Goals / Non-Goals

**Goals:**
- 月曆任一日期皆可點擊展開查看明細
- 有打卡的日子顯示 8 項任務完成狀態，視覺語彙比照管理後台個人逐日明細表既有的小方塊呈現
- 未打卡的日子清楚呈現「沒有資料」而非誤導性的「全部未完成」

**Non-Goals:**
- 不改變月曆格子本身的上色邏輯（`getCalendarColor`）
- 不在此次新增「編輯當日打卡」的捷徑——點擊只用於查看，不提供編輯入口（編輯走既有打卡頁「修改今日」流程，且僅限當日）
- 不改變既有備註/請假事由/日出照的顯示方式或位置

## Decisions

### 1. `calendar[]` 新增 `tasks` 欄位，直接從既有查詢結果取值，不新增查詢
**選擇**：`app/api/stats/dashboard/route.ts` 組 `calendar[]` 的迴圈中，`rec`（來自 `monthRecs.find(r => r.date === d)`）本身就含有 `tasks: boolean[]`（`RECORD_COLS_STATS` 已包含該欄位），直接設定 `tasks: rec?.tasks ?? null`。

**理由**：零額外查詢成本，資料本來就在記憶體裡，只是先前沒有透出。

### 2. 放寬點擊條件：從「有 note 才可點」改為「任一天皆可點」
**選擇**：`CalendarGrid` 的 `handleClick` 移除「無 note 則不展開」的提前返回，改為任一天點擊皆切換展開/收合；面板內容依資料狀態分流：
- 有 `tasks`（即有打卡紀錄）→ 顯示 8 項任務勾選方塊 + 既有備註/請假事由（若有）
- `tasks === null` 且非請假 → 顯示「當日未打卡」提示文字
- 請假（`isLeave`）→ 維持既有請假事由顯示（不受本次影響）

**理由**：符合使用者訴求「下鑽查看當日打卡了哪些項目」——這個需求不應該被「有沒有備註」這個無關的前提擋住；放寬後多了「可點但沒什麼可看」的未打卡日，用一句提示文字處理，不會造成空面板的困惑。

**替代方案考慮**：維持「有 note 才可點」，另外加一個固定顯示在月曆格子裡的小圖示表示「有明細」——會讓月曆格子更擁擠，且「有 note 才可點」這個前提本身就不直觀（使用者不會知道為什麼有些日子能點、有些不能），不採用。

### 3. 8 項任務的視覺呈現沿用管理後台既有的小方塊語彙，而非重新設計
**選擇**：面板內新增一列 8 個小方塊（比照 `app/(main)/admin/page.tsx` 個人逐日明細表的 `TASK_ABBR` 小方塊：完成為實心色塊＋✓，未完成為灰色＋·），搭配任務全名的 tooltip 或簡短標籤。

**理由**：專案已有這套視覺語彙（管理後台），重用能維持一致性、不需要重新設計一套新圖示系統；學員與管理員若都看過兩種介面，認知負擔更低。

## Risks / Trade-offs

- **[風險] 月曆格子點擊條件放寬後，手機上誤觸展開/收合的機率增加** → 可接受：既有互動已經是點擊展開/再點收合，行為一致，只是觸發範圍變大；且面板本身不是破壞性操作（純顯示），誤觸代價低。
- **[Trade-off] 不提供點擊後直接編輯的捷徑** → 可接受：編輯本來就只能動當日紀錄（`PATCH /api/checkin/submit` 限制僅當日可修改），月曆上任意一天的下鑽主要用途是「回顧」，不是「修改」，維持現有編輯入口（打卡頁「修改今日」）不混淆兩種操作意圖。
