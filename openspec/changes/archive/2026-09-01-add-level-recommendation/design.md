## Context

每月 25 日後學員於 dashboard（`app/(main)/dashboard/page.tsx` L303–315）選下月階梯，`POST /api/auth/next-level` 寫 `member.next_level`，settlement（次月 1 號 13:00）套用 `next_level → level`。目前選擇無任何依據。

階梯經濟結構（`lib/constants.ts`）——門檻越高罰金越低，使「選哪階」不直覺：

```
        門檻    未達標罰金
黃金    80%    NT$200
白銀    70%    NT$300
青銅    60%    NT$400
```

探索定調：推薦「站穩你做得到的那一階」——依上月完成率取「能達標的最高階」。此規則天然避開「精算最少罰金」（門檻高罰少）的反教育誘因，照建議走者下月極可能達標。

**實測（2026-07 已月結 22 人）**：規則跑出 1 黃金 / 5 白銀 / 16 青銅，含 3 升階（92%→黃金等）、5 降階（黃金 55%→青銅等），方向合理。但「16 人被推青銅」揭露：完成率普遍偏低 → 多數人只穩得住青銅。→ 決策：接受誠實，加成長文案給方向，不假掰包裝。

## Goals / Non-Goals

**Goals:**
- 純函式 `recommendLevel(rate, maxScore)`：rate 對照門檻取能達標最高階；豁免/無資料回 null。
- dashboard 選階區標「⭐建議」+ 情境成長文案；三階維持可選。
- 婉轉降階、青銅給成長方向。

**Non-Goals:**
- 不改階梯門檻、罰金、選擇機制、計分、月結。
- 不看多月（只看上月，探索定調）。
- 不做「各階達標機率/罰金」展開預估（只標建議 + 一句理由）。
- 不鎖定學員只能選建議階（推薦是引導）。
- 不做精算最少罰金的推薦（反教育）。

## Decisions

### 決策 1：`recommendLevel(rate, maxScore)` 純函式
```
if (maxScore <= 0 || rate == null) return { level: null, reason: '首月自由選' }
if (rate >= 80) return { level: '黃金戰士', ... }
if (rate >= 70) return { level: '白銀戰士', ... }
return { level: '青銅戰士', ... }   // <70 含 <60
```
- 門檻用 `LEVEL_THRESHOLDS`（0.80/0.70/0.60）換算百分比比對。取「能達標的最高階」= 由高到低第一個 `rate >= 門檻×100` 者。
- `maxScore<=0` 判斷豁免/無資料，沿用 pace-status 同一陷阱處理（避免豁免 rate=0 被當「完成率 0%→青銅」）。

### 決策 2：「上月」= 相對當前月的前一個已月結月
- 25 日選階時，「上月」是**上一個完整月**，該月 settlement 已在本月 1 號跑完，`monthly_summary` 有資料。
- dashboard route 取 `getYearMonth(前一月)` 的 `monthly_summary`（rate、max_score）。實作以「當前 yearMonth 減一月」推導上月字串。
- 邊界：跨年（1 月選階看去年 12 月）——月字串減法需正確處理，用日期運算而非字串拼接。

### 決策 3：成長文案四情境（依建議階 vs 現階）
- 比 `recommend.level` 與 `member.level`：高→升階鼓勵；等→維持肯定；低→降階婉轉。
- 建議青銅且離白銀有距離（rate < 70）→ 附「離白銀差 (70−rate)%」給方向。
- 文案為建設性語氣，降階不用「退步/降級」。文案可於純函式回 `reason`，或前端依 level+現階組——採**純函式回結構化欄位（recommendLevel + 現階比較），前端組文案**，便於調文字不動邏輯。

### 決策 4：呈現於既有選階區，標建議、三階可選
- L303–315 既有三顆階梯按鈕：在 `levelRecommendation.level` 那顆加「⭐建議」標記 + 上方顯 `reason`。三顆按鈕 onClick（`setNextLevel`）不變，學員可選任一階。
- 已選下月階梯者（`user.nextLevel` 有值）維持既有「✓ 下月已選」顯示，推薦可仍顯供參考或隱藏（實作採：已選則淡化推薦，仍可改選）。

## Risks / Trade-offs

- **[滿街青銅打擊士氣]** 多數人被推青銅（實測 16/22）。→ 接受誠實 + 成長文案（「離白銀差 X%，下月衝」）轉「認命」為「階段目標」。規則不變，差在措辭溫度。
- **[豁免 rate=0 誤判]** 上月豁免者 rate=0，直接套規則會推「青銅+差 60%」很荒謬。→ `maxScore<=0` 過濾，歸「無資料」。此為探索明確標出的坑。
- **[跨年月字串]** 1 月看 12 月，減月需日期運算。→ 用 Date 或既有 helper，不用字串拼接。
- **[推薦被當強制]** 學員可能以為只能選建議階。→ spec 明訂三階可選，UI 三顆按鈕都作用；文案用「建議」非「必須」。
- **[精算誘因]** 有人發現「黃金罰最少」想鑽。→ 推薦不玩精算、只推「做得到的階」；但系統仍允許自由選，鑽漏洞是既有機制問題，非本功能引入。

## Migration Plan

- 純衍生 + 呈現：`lib/scoring.ts` 加 `recommendLevel`、dashboard route 撈上月 summary + 回 `levelRecommendation`、dashboard page 選階區標註。無 schema、無 migration、無環境變數。
- 回滾：移除純函式 + 回傳欄位 + 前端標註。
- 驗證：`recommendLevel` 各門檻邊界（80/70/60、豁免、無資料）；以 2026-07 實測 22 人回歸（1 黃金/5 白銀/16 青銅）；跨年月字串；手動於 dashboard 25 日後看建議標記與文案、確認三階仍可選。

## Open Questions

- 成長文案的實際句子（升階/維持/青銅/降階四版）——design 定情境，實作時定稿文字；可上線後依觀感調。
- 已選下月階梯後，推薦要「淡化仍顯」還是「隱藏」——傾向淡化仍顯（供反悔改選參考），實作可調。
- 是否要在推薦旁極簡標「上月完成率 X%」讓學員知道依據——傾向顯，透明化推薦來源；非核心，可加。
